# Changelog

Kept in the shape of [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), dated rather than numbered, and with no `Unreleased` section — a skill is read at whatever revision you have checked out, so whatever is on the default branch is what everyone already has, and a section for work that has landed but not shipped would never close

## 2026-09-07

### Fixed

- **`-m rust` reddened every healthy `cargo test`.** `markers/rust.txt` carried `0 filtered out; finished in`, meant for a filter that matched nothing, and that is the line every full run prints for every target: a filter that matches nothing prints `N filtered out` with N above zero. The marker is gone, and the gate could not have caught it because a healthy run was kept only for pytest. There is one now for every ecosystem set, `tests/fixtures/clean/<name>.log`, each captured from a real run of the tool in the conditions the set is meant for, and every marker must stay quiet on its own, every default one on all of them
- **an `allow` regex grep could not compile turned every run into a pass.** The excuse list is applied with `grep -Ev` before the scan; a regex grep rejects left the filtered log empty, an empty log has no markers, and `run` reported `pass — log clean` for a run that said `collected 0 items`. The worst shape a guard can take, because a typo in the excuse list switched the whole check off without a word. `run` now refuses such a regex before the command starts, with exit 64, and the scan itself reports a filter that did not run as a finding rather than as silence
- **a symlink to `t.sh` refused every run.** `ln -s .../t.sh ~/.local/bin/t.sh` is how the harness gets onto a PATH, and it looked for `markers/` beside the link rather than beside the file, so every run through the link exited with "holds no markers". The path is resolved through symlinks now, absolute and relative, without `readlink -f`, which macOS only gained in 12.3
- **`bisect` skipped every commit where `make test` failed.** The probe took the command's exit 2 and 3 for the harness's own "could not run it" and "did not really run", and GNU make exits 2 on any error, so a bisect over a Makefile-driven suite stepped over every bad commit and named nobody. The probe reads the kind of verdict from `run`'s sidecar now and leaves the numbers to the command. Two more corrections on the way: a runner that is not executable (126) is skipped like one that is missing (127), and a run stopped by a person, Ctrl-C or a TERM, is passed through so git aborts the session instead of recording the interrupted commit as bad. A crash is still bad
- **every `falsify` mutant was `unusable` under the bash macOS ships.** bash 3.2 keeps the quotes around the replacement in `${content//"$find"/"$replace"}` as literal text, so the edit written was `"if false"` and nothing built. Found by running the gate under a real 3.2, which is what replaced the grep for bash-4 syntax. The edit is made by cutting around the one occurrence now, which also keeps a `&` in a replacement literal on bash 5.2, where an unquoted one would have meant the match itself
- **Ctrl-C did not stop `falsify`.** Its interrupt handler restored the source and returned, and a handler that returns lets the script carry on: the loop ran the next defect, the interrupted one vanished from the report, and the summary still counted it. The handler now restores and then dies of the same signal, so the caller sees an interrupt and not a shorter report
- **`falsify` reported a mutant it could not write as a survivor.** The edit was written without checking the write. On a read-only source file it failed silently, the suite ran against the pristine code and passed, and a guard the suite does cover was reported as one nobody checks. A write that fails is fatal now, exit 70, with the tree untouched
- **`flaky` could refuse without a word.** It muted each run's output, and `run`'s own refusals went with it, so `flaky 3 -x -- cmd` exited with a usage status and an empty terminal. Flags and marker sets are now checked before the first run, and a refusal `run` can only make once the loop has started is shown rather than swallowed
- `run -t abc` silently meant no tail, because bash arithmetic reads a word as zero; it refuses now. A marker set named twice, on the line or once in the config and once on the line, printed every finding twice; it is loaded once
- **the flake named a platform it could not be evaluated for.** `systems` listed `x86_64-darwin`, and nixpkgs 26.11 has dropped it, so `nix develop` there died on evaluation rather than opening a shell. `nix flake check` never said so because it reads only the system it runs on, and the gate had never looked at `flake.nix` at all — the file that decides which tools every check runs with was the one file nothing checked. The entry is gone, Apple having stopped selling those machines in 2023 and the macOS runner being Apple silicon, and the gate now evaluates every system the flake claims, in one offline eval, with the list read out of the flake rather than repeated
- **the gate warned about itself on every run and still printed `everything holds`.** `flags_of` reads the parsers out of `t.sh` with an escape POSIX leaves undefined, `\ ` for a space, and gawk said so twenty-nine times in a run that ended green. Nothing was computed wrongly — gawk, mawk, busybox awk, goawk and the one-true-awk macOS ships all read it as a space, checked — but a green run whose log carries a warning is the exact shape this skill exists to refuse, and finding it in the gate's own output is the argument for the rule. The escape is gone, `flags_of` is now held to writing nothing on stderr, and `gawk` is pinned in the dev shell so that proof fails for the defect rather than for whichever awk a contributor has

### Changed

- **the core gains three rules and changes one.** Never weaken a check to get a green run; evidence is a run made after the last edit and read by someone other than the author of the claim, which is why a session that wrote both the code and its tests needs a constraint from elsewhere; three failed fixes mean the model is wrong, not the fix. And a test and the code it pins are one commit, with the red watched before it and `t.sh prove` demonstrating it afterwards, where the rule used to ask for the failing test as a commit of its own. A closing checklist, "Before you say it works", points each item at the reference that decides it. The file is held under ninety lines by the gate, so the core stays the part that is read on every trigger
- **the harness's own exit codes moved out of the range test runners use.** `run` reported a lying log as 3, `flaky` reported disagreement as 4, and every usage or harness error was 2. GNU make exits 2 on any error, pytest uses 2 to 5, `mix test` fails with 2, and cargo-nextest exits 4 for "no tests ran", so a probe that skipped on 2 skipped every commit where `make test` failed, and a `flaky` verdict was indistinguishable from nextest's own empty run. The verdicts now sit in a band nothing else claims: 64 for a usage error, 70 for a failure of the harness itself, 79 for a run that exited 0 while its log said otherwise, 86 for runs that disagreed. Anything checking the old numbers must be updated
- **the bash-3.2 guard is a bash 3.2.** The gate grepped the scripts for constructs newer than the bash macOS ships, and a grep matches the constructs somebody thought to list: on its first audit it let nine through, `local -n`, `|&`, `;;&`, `${x@Q}`, `exec {fd}<`, `read -t 0.5`, `wait -n`, `${s:0:-1}`, `globstar`. The guard and its fixture are gone. In their place CI runs the behaviour half of the gate on a macOS runner under `/bin/bash`, with a `declare -A` and a `mapfile` planted in copies of `t.sh` that must fail there, so the proof is about the interpreter and not about a list
- **`falsify` tells a weak suite from a rotten list.** A `stale` entry and an `unusable` one were counted among the survivors, so the report blamed the tests for a defect list nobody had maintained, and CI saw one exit code for three different problems. The summary counts `caught`, `SURVIVED`, `stale` and `unusable` separately, and the exit code says which one ended the run: 83 for a survivor, 87 for a stale list, 88 for an edit that only broke the build; a suite that was red or never ran before any edit is 85 rather than a usage error. The verdict of each run comes from `run`'s sidecar, so a suite whose own exit code is 79 is no longer mistaken for a harness verdict
- `flaky`, `bisect` and `bisect-probe` name the flags they forward to `run`, `-m`, `-p`, `-t`, and `-l` where the logs may go, and refuse anything else before the first run, where they used to sweep any word up and hand it on. The gate reads accepted flags out of each parser, and a documented `t.sh flaky 20 -m rust` was being flagged as impossible

### Added

- four more ecosystem references, [jvm](references/ecosystems/jvm.md), [.net](references/ecosystems/dotnet.md), [php](references/ecosystems/php.md) and [playwright](references/ecosystems/playwright.md): the wrapper over the global tool, the native fail-on-nothing-ran switch of each runner and how its default stands, the lines a green run prints while lying, the determinism traps, what makes a usable defect entry there, and a recipe for keeping a healthy run and a lying one so a marker set can follow. No marker set ships for them yet, because a marker is added only with a real line from a real run behind it; every existing reference gains the same "fail on nothing ran, natively" section
- **`t.sh help [SUBCOMMAND | codes]`** is the reference, as its own subcommand rather than the file's header: one section per subcommand with every flag, the flags every subcommand forwards to `run`, the policy keys, the `T_ALLOW`, `T_LOGDIR`, `T_LOGFILE` and `T_CONFIG` variables, and the exit-code table. The header of `t.sh` is a short description again. The gate reads every subcommand out of the dispatcher, every flag out of every parser, every variable and every exit code out of the script, and requires each to be in the help, so the text cannot drift from the code
- **`t.sh prove [REF] -- CMD`**, the revert-to-verify ritual done by the harness: the files of one commit, HEAD by default, are split by the rule `falsify` uses for a defect's file, the test files stay and the rest is the fix; the suite must be green with the fix in, then the fix is taken back to what it was before the commit, a file the commit added removed and a file it deleted brought back, and the suite must go red. `proven` exits 0; `VACUOUS`, the tests passing without the fix, exits 83 with an annotation on each file on a GitHub runner; a fix without which nothing builds is 88, a suite that does not finish 84, a suite already red 85, a commit that changes no source file a usage error. An older commit is proven in a worktree at that commit, so the tree in front of you is left alone. This is what "a test and its fix are one commit" costs: the commit has to demonstrate itself
- `templates/defects.sh` now says which defects to write and in what order: first the whole body of a function replaced by a constant, the edit that finds the six to fifty percent of "covered" functions no test would miss, then one guard neutered at a time; never against logging, formatting or a trivial accessor, about seven per file, one per behaviour; with a declared exception shown. The gate parses the template through `falsify` itself
- `falsify --worktree` edits a checkout of HEAD in a git worktree rather than the files in front of you. In place, a format-on-save, a file watcher, an editor's auto-fix or a commit made mid-run all see the mutant, and the run has to be left alone for as long as it takes; in a worktree none of that can happen, at the price of a build that starts from nothing. Either way a marker names the defect in flight, `FALSIFY-IN-PROGRESS` at the root of the worktree or `in-flight` under `falsify.out/`, so a mutant that somehow outlives a run is found by the name of what put it there
- `falsify --since REF` runs only the defects in files changed since REF, which is the run for a pull request, with the full list kept for the default branch. It is a filter and not a proof, a change in one file breaks the tests of another, so an empty selection is said out loud rather than passed in silence
- on a GitHub runner every `falsify` finding is also an annotation on the file and line, an error for a survivor and a warning for a stale, unusable or timed-out entry, so it shows in the diff of the pull request. A finding in a log is read by whoever opens the log; one next to the code is read by whoever is about to merge it
- **a defect nothing can catch is declared where it is written**: `defect ... expect survived "reason"`. Some edits change the code without changing anything a caller can observe, and a list that has to leave them out loses the record that somebody looked. Declared, the defect is reported `expected` rather than `SURVIVED`, and the day the suite does catch it the declaration is reported `stale`, exit 87, so an exception cannot outlive its truth. On the line and not in a separate list, because an exception kept elsewhere is one nobody rereads
- a `SURVIVED` line is followed by where the edit was and what it was, `FILE:LINE  - before` and `+ after`, because a survivor is only actionable next to the code it names; `results.json` carries the line too
- `falsify` refuses a defect aimed at a test, vendored or generated file, `tests/`, `*_test.*`, `*.spec.*`, `vendor/`, `node_modules/`, `*_pb2.py` and the like: a test file is executed, so an edit there is "caught" by whatever it breaks and reads as coverage the suite does not have. `--any-file` is for a list that knows better
- **`falsify` leaves what it found in `falsify.out/`**, or `--out DIR`: one file of defect names per verdict, `caught.txt`, `survived.txt`, `stale.txt`, `unusable.txt`, `timeout.txt`, which is what a diff between two runs or a grep in CI wants; one log per defect under `logs/`, the baseline's included; and `results.json` with the verdict and consequence of every defect for whatever reads machines. Written as the run goes, so an interrupted run still leaves what it had found. Add the directory to `.gitignore`
- **`falsify` holds every run to a deadline.** A neutered guard is often a loop that no longer ends, the increment removed from a counter being the canonical case, and one such defect used to hang the whole falsification. The unbroken suite is timed first; each mutant then gets five times that or twenty seconds, whichever is more, or `--timeout SECONDS`. A run that does not finish is reported `TIMEDOUT` and exits 84: not caught, which would reward the suite for a hang, and not survived, which would blame it for an edit that never let it answer. The suite runs in its own process group, so the deadline ends the runner and everything it spawned, without GNU `timeout`, which macOS does not have
- `.github/dependabot.yml` watches the action pins weekly, grouped into one pull request, as the [ci](https://github.com/rokokol/ci-skill) skill's pinning rule has always said and no repository in the family did. The gate requires the file
- the gate now runs the [ci](https://github.com/rokokol/ci-skill) skill's two travelling checkers, copied verbatim: `check-skill.sh`, which proves SKILL.md loadable, walks the links from it to require every reference reachable, and resolves every link and anchor with GitHub's own slug rules; and `check-pins.sh`, which greps the workflows for fourteen shapes of unpinned registry lookup and proves on every run that it catches each of them. Both falsify themselves on copies of the repository. Adopters get the same two files from the ci skill
- `bisect` reads what git said instead of passing git's status through. A culprit is named on its own line and exits 0; a history where only commits that could not answer are left between good and bad is reported `INCONCLUSIVE` with exit 89, where before git's own nonzero came back looking like a usage error. git's session log is saved beside the run's logs as `bisect.log`, so a wrong answer can be corrected with `git bisect replay`. `--first-parent` and `--no-checkout` are passed through to `git bisect start`, and a bisect already in progress is refused rather than silently reset, which is what `git bisect start` does on its own
- `run` writes the kind of verdict it reached, `pass`, `fail` or `lied`, beside the log as `LOG.verdict`. A number cannot carry it: the command's own 79 would read as the harness's. The other subcommands read the sidecar instead of guessing from the status, and a wrapper of your own can do the same

## 2026-09-05

### Fixed

- **the harness needed a bash newer than the one macOS ships.** `[[ -v VAR ]]` is bash 4.2+ and broke `run` outright on a macOS runner; `declare -A` in `falsify` is 4.0+ and would have broken it next. Both are gone — the first was a redundant clause, the second became two parallel arrays, which for a handful of paths costs nothing. Reported from a CI run on a machine none of this was written on, which is the only place it could have been found. A guard now greps every shipped script for constructs a bash 3.2 or a BSD userland does not have, with each literal split so the pattern cannot match its own source, and the planted constructs kept in a fixture for the same reason

- **a marker file checked out with CRLF reported every healthy run as a lie.** A blank line became a marker of one carriage return, `grep -F` found that on every line of a CRLF log, and a passing `cargo test` was reported as `LIED` with a build line offered as the evidence. The trailing CR is stripped when reading marker files and `tests/t.conf` now, and a CRLF fixture holds it. Found on a Windows runner by somebody using the skill, where git's autocrlf converts on checkout — the worst shape a marker bug can take, since a check that reddens good runs is a check that gets switched off

- **the "able to fail" proofs had stopped proving anything.** Adding the `actionlint` step made every throwaway copy die there, before it ever reached its planted defect — so each `! nested` assertion held for the wrong reason, and the gate stayed green while sixteen falsifications were vacuous. Two guards now make that unrepeatable: an untouched copy must pass before any defect is planted, and each planted defect must produce **its own** failure message rather than merely some failure. The second guard immediately found the duplicate-marker rule unproven as well — its copy was failing on the dead-entry rule first, so the rule it was written for had never run
- `flaky` ignored the `logdir` its repository names in `tests/t.conf`, writing where `run` would not. It reads the same policy now

### Changed

- the markers of a lying run moved out of `t.sh` into `markers/*.txt`, so the list grows as data without touching the harness. `markers/default.txt` always applies; `-m NAME` adds a set shipped beside the script and `-m path/to/file` one of your own. `check.sh` reads the same files `run` reads, and requires every entry to catch a line in its set's fixture, so a dead marker cannot sit there looking like a guard. A set that resolves to nothing — missing, empty, misspelled — refuses to run rather than passing quietly
- `tests/t.conf`, a repository's own testing policy: which marker sets apply, one-off patterns, the excused-lines regex, the log directory ([template](templates/t.conf)). Read from the current directory only — no search up the tree, because a config found three directories away is a config nobody knew was in effect — and it **never carries the command**, which stays after `--` so a green run's subject is visible where its verdict is. An unknown key, a key with no value or a marker set that does not exist stops the run and names the line: a typo that is skipped leaves a repository believing in markers that were never loaded, which is worse than having no config at all
- six per-ecosystem marker sets ship beside the default one — `pytest`, `shell`, `go`, `rust`, `node`, `cpp` — each opted into with `-m NAME` and each with its own fixture, so the knowledge in `references/ecosystems/` is now executable rather than only readable. No ecosystem set may repeat a default entry, which the gate enforces: the default applies to every run already, so the copy would be dead weight reading as extra coverage
- the refusal above had to be moved out of `scan_log`, which runs inside a `$(...)`: `die` there exits the subshell and the caller carries on with an empty result, so a guard written that way does not guard. Written as it was, an empty marker list would have made every run a pass while the check still looked like it was working

### Added

- the skill itself: a core of rules that hold in any language — the command's own status rather than a pipe's, the log read even at exit 0, nothing claimed until it has been run and watched, test-first with a falsification pass behind it, one logical change per commit, unstable tests fixed or quarantined but never retried, no shim for a shape that was never released, and a running todo list — plus the two modes (`tdd`, `falsify`) those rules are applied in
- `t.sh`, the harness: `run` (honest status out of `PIPESTATUS`, the whole log kept, the log scanned for markers of a run that did not happen, the tail printed only after the verdict is already decided), `flaky` (N runs, how many disagreed), `bisect` (`git bisect run` with a status mapping that skips what cannot answer and clamps a crash so it cannot abort the session) and `falsify`
- `falsify` applies hand-written edits from the repository's own `tests/defects.sh` and reports `caught` / `SURVIVED` / `stale` / `unusable`. Build and test are separate phases, so an edit that stops the code compiling is `unusable` rather than credited to the suite — without that distinction every syntax-breaking edit in a compiled language would read as coverage that does not exist
- references: verdict, tdd, falsifiability, flaky, commits, no-legacy, layers, and one per ecosystem for pytest, shell/bats, go, rust, node, typescript and c++
- `check.sh`, the self-testing gate: the marker table is read out of `t.sh` instead of being spelled twice, every marker must catch its fixture and stay silent on a healthy one, and every check is proven able to fail against a deliberately broken copy — a dead marker, a marker that cries on a good run, a harness reading `tee`'s status, a subcommand missing from the help, a bisect passing statuses through raw, a restore losing the trailing newline, a `SKILL.md` with no frontmatter, an unreachable reference, a dead link and a dead anchor

### Notes

Three of the checks above found real bugs while being written, which is the point of the rule they enforce: a `PIPESTATUS` guard that `pipefail` had made untestable, a falsify restore that lost the trailing newline through command substitution — with a check that missed it by making the same mistake on both sides of the comparison — and a bisect fixture whose answer was genuinely ambiguous.
